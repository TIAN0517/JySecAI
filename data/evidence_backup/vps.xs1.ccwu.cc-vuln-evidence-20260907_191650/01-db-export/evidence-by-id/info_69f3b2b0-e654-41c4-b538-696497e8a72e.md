## Description

4004 auth 服务 13 个用户管理端点（activateAccount/enableAccount/resetPassword/setUserPermissionMap/disableAccount/Users/Roles/Permissions/Branches）所有 HTTP 方法 53 用例 100% 返回 401，统一走 express-jwt 中间件；业务层无未鉴权端点；唯一不走 JWT 的是 /Users/changePassword（已 200+ 用例 100% 闭合，业务层对 NoSQL/SQLi/类型混淆严密防御）；唯一信息泄露是确认后端为 MySQL + Sequelize ORM + bcrypt（严重信息泄露但非可利用漏洞）。

## Preconditions

无前置条件（完全匿名测试）

## Reproduction

1. 直接访问 `PUT https://epcr.tpf.gov.tw:4004/Users/activateAccount/1`，HTTP 头 `Content-Type: application/json` + `Origin: https://epcr.tpf.gov.tw`，body `{"a":"b"}`
2. 观察响应：HTTP 401 + 183B + `{"name":"Unauthorized","message":"No authorization token was found","code":401}`
3. 遍历所有 13 个端点的所有 HTTP 方法（GET/PUT/POST/PATCH/DELETE）—— 全部统一 401 响应
4. 尝试 `/Users/changePassword` 业务层注入（88 用例矩阵）—— 全部 403/500（无 200）
5. 观察 Oracle：account 字段 NoSQL 操作符 + SQL 字符串注入 + 类型混淆 + 真实密码组合—— 业务层严密防御
6. 结论：所有用户管理端点鉴权严密，业务层无可利用漏洞

## Impact

**严重性：info（无可利用漏洞）**
- ✅ 正面：所有用户管理端点鉴权严密，无法绕过
- ✅ 正面：业务层对 NoSQL 操作符注入、SQL 字符串注入、类型混淆严密防御
- ⚠️ 信息泄露：暴露后端架构（MySQL + Sequelize ORM + bcrypt）、表名 `User`、字段 `disabled`
- ⚠️ ORM 拼接漏洞：Sequelize 未参数化 SQL（但被业务层 val.replace 字符串验证前置阻断）
- 这些信息泄露降低了后续攻击的难度，但本身不构成可利用漏洞
- **业务影响：低**；用户管理功能在认证层面是安全的

## Recommendation

**无需修复（无可利用漏洞）**
- ✅ 用户管理端点鉴权严密：所有端点都走 express-jwt，强制 JWT 鉴权
- ✅ /Users/changePassword 业务层严密：val.replace 字符串验证阻断 NoSQL/SQLi 注入
- ⚠️ 建议加固（非紧急）：
  1. 抑制 Sequelize 数据库错误堆栈返回（生产环境应禁用错误详情）
  2. 修复 Sequelize ORM 拼接漏洞（参数化 SQL 防止 SQLi）
  3. 在错误响应中只返回通用错误消息（如 "Internal Server Error"）
- 修复后复测方法：尝试同样 88 用例矩阵应全部 403 + 通用 500 错误（无 ORM 堆栈泄露）
