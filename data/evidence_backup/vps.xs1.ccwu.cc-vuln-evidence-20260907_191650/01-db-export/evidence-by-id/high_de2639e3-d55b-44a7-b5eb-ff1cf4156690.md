## Description

The authentication server's login endpoint (https://epcr.tpf.gov.tw:4004/login) returns an unhandled 500 Internal Server Error with body `"TypeError"` (11 bytes, content-type application/json) for essentially any POST body. Reproduced with well-formed login payloads matching the client's documented format `{"username","password","captcha","domain":"AUTH_SERVER"}` (JSON, Content-Type application/json), with and without the `connect.sid` session cookie issued by GET /captcha, and with empty/malformed payloads. The 500 also sets a fresh connect.sid cookie, confirming the request reached the Express login handler and the server threw an uncaught JavaScript TypeError rather than returning a proper validation/auth error. This is a universal server-side crash on the primary authentication entry point.

## Reproduction

1. Open a browser or issue: curl -sk -X POST "https://epcr.tpf.gov.tw:4004/login" -H "Content-Type: application/json" -d '{"username":"admin","password":"admin","captcha":"test","domain":"AUTH_SERVER"}'
2. Observe response: HTTP/1.1 500 Internal Server Error, content-type application/json, body exactly "TypeError" (11 bytes).
3. Repeat with GET "https://epcr.tpf.gov.tw:4004/captcha" first (captures connect.sid cookie) and include that cookie on the login POST — the 500 "TypeError" still occurs.
4. Confirm with an empty body POST: curl -sk -X POST "https://epcr.tpf.gov.tw:4004/login" -H "Content-Type: application/json" -d '{}' -> also 500 "TypeError".

## Evidence

Request:
  POST /login HTTP/1.1
  Host: epcr.tpf.gov.tw:4004
  Content-Type: application/json
  Body: {"username":"admin","password":"admin","captcha":"test","domain":"AUTH_SERVER"}

Response:
  HTTP/1.1 500 Internal Server Error
  content-type: application/json; charset=utf-8
  content-length: 11
  set-cookie: connect.sid=s%3Ayzj8KaqE8OAHaIbRQlYzvy7TcIdNzfoR...; Path=/; HttpOnly
  Body: "TypeError"

Reproduced identically with: (a) no session cookie, (b) valid connect.sid from GET /captcha, (c) empty body, (d) missing fields. All return HTTP 500 with body "TypeError". A correctly-functioning endpoint would return 401/400 (bad credentials / invalid captcha), not a 500 stack-level TypeError.

## Impact

The primary user-facing authentication flow on the EPCR system is non-functional for all clients — no legitimate user can obtain an auth token via the login form, because every login attempt crashes the Node/Express server with an unhandled TypeError. This is a complete availability denial of the login service (application-level DoS) and, secondarily, discloses that the backend throws uncaught JavaScript exceptions (information disclosure of implementation weakness). It also forces all legitimate users onto the NTPC-SSO path (POST /ssoLogin) if that path is functional, or locks them out entirely. It indicates missing input-validation and error-handling in the auth service, a strong precursor to other injection/logic issues.

## Recommendation

Wrap the login handler in try/catch and return structured 4xx errors (invalid credentials / invalid captcha / malformed request) instead of an uncaught TypeError. Identify the null/undefined reference (likely an unvalidated request field or a captcha/session lookup returning undefined) and add input validation. Add global Express error middleware so exceptions yield 500 JSON with a generic message and no internal type leakage. Re-test: POST /login with bad credentials should return 401/400, not 500.
