## Description

4001 vitalSignVideoServer PUT /imageData/{id} 端点存在 Sequelize update 内部错误:对存在 id 的 PUT 请求(任意 body 包括空 {})均返回 500 {"message":"internal error","errors":["Invalid parameters."]}。该错误源自 Sequelize Model.update() 内部 try/catch,非用户 validation,而是 ORM 内部 SQL 参数绑定失败。这构成了稳定的 oracle:1) 区分 id 存在性 (404 vs 500),2) 暴露 ORM 实现细节。攻击者可利用此 oracle 枚举 id 范围(无认证),确认存在的数据范围;若结合 recordUuid 索引,可全表枚举敏感记录 (预计 imageData 表含 1,445,571 条心电图/影像元数据)。注意:id=1 不存在时返回 404(路由层检查),id=10000/1011277 存在时返回 500(ORM update 流),这是稳定的二分枚举 oracle。

## Reproduction

1. 打开终端,确认可达 https://epcr.tpf.gov.tw:4001
2. 执行 curl:
   curl -sk -X PUT "https://epcr.tpf.gov.tw:4001/imageData/10000" \
     -H "Origin: https://epcr.tpf.gov.tw" \
     -H "Content-Type: application/json" \
     -d '{}' \
     -w "\n[HTTP %{http_code}]\n"
3. 观察响应:HTTP 500 + {"message":"internal error","errors":["Invalid parameters."]}
4. 对比测试:
   curl -sk -X PUT "https://epcr.tpf.gov.tw:4001/imageData/1" \
     -H "Content-Type: application/json" \
     -d '{}'
5. 观察响应:HTTP 404 + {"message":"Not Found","errors":[]}
6. 利用差异:对 id=1 到 id=1,445,571 全范围 PUT 测试,可构建稳定的存在性 oracle

## Impact

MEDIUM 严重性。三个影响维度:
1. **稳定 oracle 利用** - PUT /imageData/{id} 端点对 id 存在性返回不同响应 (404 vs 500),可作为基于 oracle 的盲注枚举原语。虽然 GET 端点本身已可枚举 (200 vs 404),但 PUT oracle 提供了独立的、利用 update 流时序的枚举通道。
2. **暴露 Sequelize ORM 内部错误** - "Invalid parameters." 错误信息暗示这是 Sequelize Model.update() 的内部 try/catch,泄露技术栈细节,辅助后续针对性利用。
3. **POST 等价 oracle** - 已发现 POST /trendings `hr:{$gt:x}` 触发相同的 `val.replace is not a function` 500 错误,可作为 POST oracle 使用。
4. **潜在的 update 污染攻击面** - 虽然当前所有 body 触发 500,但如果后端修复 validation,可能开启 update 路径的攻击面 (PUT 资源级 IDOR)。

利用场景:
- 攻击者可对 id=1 到 id=1,445,571 全范围进行 PUT oracle 探测,确认实际存在的数据范围 (无需 GET)
- 若 ID 是顺序递增,可估算数据库规模
- 与 GET 端点的 NoSQL $where/$regex 配合,实现基于 oracle 的盲注

## Recommendation

修复建议:
1. **立即修复 PUT update 流** - Sequelize Model.update() 内部 try/catch 应返回 400 Bad Request 而非 500 Internal Server Error,避免泄露 ORM 内部错误
2. **统一错误处理** - 使用全局 error handler 将所有 unhandled error 转换为标准格式 {"message":"internal error","errors":[]} 不暴露错误细节
3. **添加认证层** - PUT /imageData/{id} 端点必须先验证 JWT token (类似 4002 REST 端点的 express-jwt 模式)
4. **添加 IDOR 保护** - PUT 操作必须验证用户对资源的权限 (recordUuid 关联用户 / 角色)
5. **日志告警** - 对所有 PUT 500 错误记录告警,识别潜在攻击行为
6. **配置 WAF** - 部署 WAF 阻断异常 PUT 请求模式

复测方式:
1. PUT /imageData/10000 (存在 id) + 任意 body → 期望 200/400 而非 500
2. PUT /imageData/1 (不存在 id) + 任意 body → 期望 404 Not Found
3. PUT /imageData/{id} 无认证 → 期望 401 Unauthorized
